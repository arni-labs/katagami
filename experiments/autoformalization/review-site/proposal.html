01 / What we formalize

Visual elements, roles, and possible uses.

The draft records visual elements, their roles, and ways to combine them. It separates instructions specific to an example page. Each entry records its source, scope, interpretation, status, and intended enforcement.

Galley

Cormorant for editorial display, Plex Sans for work text, Plex Mono for proof labels. White fields, limited paper grouping, square forms, crop marks, and rectangular colour marks.

In verdicts, cyan signals “on press,” yellow “hold,” vermilion “recut.” That does not mean every red object is a recut.

The source asks for asymmetry and substantial negative space. We retain this written norm without claiming it is necessary for perceived identity.

Aya

Light condensed serif display, monospaced labels, washi texture, ink text, charcoal areas, and role-specific colour. Display, labels, and prose have different treatments.

02 / What actually runs

A small SMT experiment.

I ran Z3 4.15.4 on a symbolic two-item model. It inspects neither screenshots nor HTML. The model defines two annotation presentations and an operation that converts an attached note into an indexed note.

  1. SAT The colour rules allow the declared attached presentation with a cyan on-press verdict.
  2. SAT The colour rules also allow the declared keyed presentation with a cyan on-press verdict. These two cases model no geometry and establish no layout feasibility.
  3. UNSAT Requiring an on-press verdict to be vermilion conflicts with the selected cyan rule.
  4. UNSAT With unique keys, no choice of owner or integer keys makes the defined transformation resolve to the wrong item.
  5. SAT Without unique keys, a wrong-owner example exists: both keys are 0, the note belongs to item 1, but lookup returns item 0.
Read the mathematical claim and solver output
owner ∈ {0, 1}
emitted_key = key[owner]
resolve(k) = first item whose key equals k

Can this happen?
key[0] ≠ key[1] AND
resolve(emitted_key) ≠ owner

Z3: unsat

Remove the unique-key assumption:
Z3: sat
key0 = 0, key1 = 0
owner = 1, resolved_owner = 0

Case sequence:
sat / sat / unsat / unsat / sat

Conflict core:
(source_on_press_cyan
 requested_on_press_vermilion)

This establishes a property of the defined two-item operation under its assumptions. It does not prove that a generated image preserves the note, belongs to Galley, or is creative. We trust Z3 here; no independent proof checker has verified a certificate.

The solver reasons about possible symbolic constructions before rendering. For this tiny example, ordinary code could also do the job. We have not shown that solver assistance is worth the complexity.

Mechanics: Z3 commands and result types; validity and conflict cores. A conflict core is not automatically minimal.

04 / Comparison

Test the description, then the solver.

  1. Prose guidance. The language, exceptions, and brief written as ordinary instructions.
  2. Structured guidance. The same semantic information organized into roles, relationships, and possible operations. No solver.
  3. Structured guidance + solver. The same description, with solver-assisted construction or repair of the symbolic plan.

All conditions get the same information, references, content, dimensions, and generation budget. Each attempt gets one initial planning call and one revision call using the same planner model and reasoning setting. Before running, we will record those settings and context packets. Solver time is an additional measured cost. We retain every output, interleave generation order, and hide condition labels for your final comparison.

Proposed size: two languages × one brief × three conditions × two independent plan-and-image attempts = 12 images. Each attempt starts from the frozen packet and cannot see another attempt's plans or images. We will record any context-isolation limitation. Built-in image generation only. The tool does not expose enough controls to promise identical seeds or backend versions.

This is a development pilot: we know these tasks while drafting the representation. A later test would freeze the description before choosing a new brief.

You judge identity, novelty relative to the source, usefulness for the brief, and craft separately. Ties, neither, and uncertainty are valid. We also record whether each image follows its plan. A valid symbolic plan can still produce a faulty image; a mockup cannot establish interaction usability.

  • Better identity alone means preservation, not improved creativity.
  • More difference without usefulness is not enough.
  • If structure helps but the solver does not, develop the description without solver machinery.
  • If neither helps, report no observed benefit. Two languages and one reviewer cannot establish a general result.
05 / Collaboration premise

What Katagami could contribute.

Katagami could supply an editable description of a language, its conventions, accepted departures, and possible transformations. A design agent could use it to solve a new brief, then create, inspect, and refine the result.

This is a proposed interface to test with Paul, not an existing Impeccable integration. We are changing no Impeccable code. The experiment asks whether the additional description helps enough to justify a collaboration.

The earlier “identity proof versus contract proof” distinction was too strong. The proposed solver checks declared relationships. People still judge whether the result feels like the language. Writing a formal rule does not establish that it describes perceived identity.
